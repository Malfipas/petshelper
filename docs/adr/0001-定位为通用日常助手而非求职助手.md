# 定位为通用日常助手而非求职助手

当时要决定的是这个产品服务什么范围：做成求职专用的准备工具，还是做成能装下任意事项的通用日常助手。决定选后者，产品结构因此定为「助手 + 多个项目」，求职、配音、毕业论文平级共存，以后想做别的事只需新增一个项目。

放弃求职专用方向的关键理由：这个产品必须靠用户愿意主动打开才能活下来，而只装"应该做的事"的产品会变成愧疚制造器，打开就看到自己没在找工作。配音这类"想做"的事不是附加功能，它是把人带进来的入口。

## Considered Options

- **求职专用工具**：范围明确、容易做深，但产品只装"该做的事"，打开即触发愧疚。
- **通用日常助手 + 项目制**：要多一层抽象（得先有项目模型），但"想做"和"该做"的事能平级共存。

## 什么情况下会推翻

如果项目模型带来的通用性反而让每一件事都定义不清、推不动，说明抽象层级过高，需要回退到更具体的形态（例如先只装两类项目，把模型收窄）。
