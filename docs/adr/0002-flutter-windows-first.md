# 用 Flutter 做 Windows 首发，AI 直连各家 API

这一份把八页原型落成代码之前必须定的五件事一次定完：用什么框架、首发哪些平台、状态怎么管、数据怎么存、AI 怎么接。五件事互相咬合，拆开单定任何一件都会返工。

## 决定一：框架用 Flutter

当时的情境：产品形态是桌面常驻窗 + 悬停面板 + 一个居中的主界面，外加托盘与开机自启。同一套界面以后要能跑到手机上，而桌面端的窗口、托盘这些能力各平台都不一样。

备选方案：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| Flutter | 一套代码跑桌面与移动端，自绘控件，观感不随系统版本漂移 | 桌面端生态比 Electron 薄，窗口与托盘要靠插件 |
| Electron | 生态最厚，桌宠类成品最多，抄现成的最快 | 打包体积大，内存常驻高；桌宠要 7×24 挂着，这两项都是持续代价 |
| 原生（WinUI） | 性能与系统融合最好 | 与移动端完全不通用，等于要写两套 |

**为什么选它**：这个产品要常驻，Electron 的体积与内存在"一直开着"这个前提下被放大；而"以后可能上手机"这件事只要还挂在需求里，原生就得写两套。Flutter 的自绘控件也正好对上方向 A 的克制界面——界面不依赖系统主题，跨端不会长得不一样。

**什么情况下会推翻**：如果 Flutter 的桌面插件在 Windows 上出现绕不过去的坑（透明窗口锯齿、托盘图标失真、拖拽跟手性不达标），且短期没有修复迹象，就换 Electron 重写桌宠这一层，业务层保留——这也是为什么领域层不许依赖 Flutter。

## 决定二：首发只做 Windows

当时的情境：用户以学生与在职的人为主，Windows 占比最高；而桌宠的窗口、托盘、自启在三个系统上各有各的写法。

备选方案：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 只做 Windows | 窗口、托盘、自启只调一遍，发布链路最短 | macOS 用户要等 |
| Windows + macOS | 覆盖面大 | 两端分别调窗口与托盘，工作量约翻倍 |
| 三端齐发 | 最广 | Linux 的输入法、托盘、自启差异最大，最容易拖垮进度 |

**为什么选它**：v1 要的是"能天天用的最小闭环"，多一个平台就多一份窗口层的调试，而桌宠的成败在形态不在平台数量。

**什么情况下会推翻**：如果内测期 macOS 用户占到三成以上，或出现"没 Mac 版就不算完成"的外部压力，就提前开 macOS 分支——窗口层已隔离在 `platform/`，加平台只改那一层。

## 决定三：状态管理用 Riverpod

当时的情境：界面有七块（桌宠、悬停面板、独立事项、记录、项目、想法盒、设置），计时状态要跨面板与列表共享，AI 调用要有加载与失败态。

备选方案：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| Riverpod | 编译期安全的依赖注入，状态与依赖一起管，测试好替换 | 概念比 Provider 多，上手有一段 |
| Bloc | 事件驱动，团队好分工 | 每个功能都要写 event 与 state，代码量约多三成 |
| setState + 手写单例 | 最直白 | 计时跨页共享必然长成一堆回调，后期没法收 |

**为什么选它**：这个产品的状态几乎都围绕"当前事务"这一个概念转，Riverpod 的 Provider 正好把它提到一处，面板、列表、记录三处读同一份。

**什么情况下会推翻**：如果状态里出现大量需要严格有序处理的事件流（比如多人协作式的操作队列），再考虑迁 Bloc；在那之前不换。

## 决定四：数据层用 drift 跑在 SQLite 上

当时的情境：要存项目、步骤、事项、流水、随手记、想法、对话、设置。流水会随时间累积，记录页要按月聚合，想法要按分类查。

备选方案：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| drift | SQL 能力完整（聚合、索引、迁移），类型安全，查询在编译期就能查出错 | 要写表定义与迁移，前期比 JSON 重 |
| Hive / Isar 这类 KV 库 | 上手快，无需写表 | 复杂查询弱，记录页的按月聚合要自己拉全量算 |
| 直接存 JSON 文件 | 最简单，原型阶段就够 | 数据一多读取全表，迁移无从谈起 |

**为什么选它**：记录页的日历热力图与项目进度都靠查询，不靠遍历；而迁移机制是"改版不能丢用户数据"的前提。

**什么情况下会推翻**：如果最终数据量始终停在几十条量级、且放弃复杂查询，可以退回轻量 KV；但流水是每天自动累积的，这一天来得比想象的快。

## 决定五：AI 直连各家 API，key 存系统安全存储；托盘与开机自启先做，快捷键后置

当时的情境：AI 能力有四处（拆解、归类、日总结、面板对话），都要一个 key。而常驻形态要求开机自己出现、随时能退出。

备选方案：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 直连各家 API，key 存本机安全存储 | 与原型一致，不养服务，不建账号 | key 在用户机器上，泄露风险由本地安全存储兜 |
| 自建后端代理 | key 不落地，可统一控成本 | 多一个服务与账号体系，v1 变重 |
| 本地小模型 | 隐私最好 | 常驻场景下速度与体积都吃力 |
| v1 就把全局快捷键做了 | 唤出更快 | 与输入法冲突，PRD 自己也记了这条风险 |

**为什么选它**：v1 不碰服务端，少一整条运维与计费链路；托盘解决"找得到、退得出"，开机自启解决"开机自己出现"，这两条是常驻的底线。快捷键与输入法冲突是已知风险，放在 v1 之后单独处理，不阻塞主链路。

**什么情况下会推翻**：如果出现"key 不能放用户机器上"的合规要求，或多模型切换导致每家都要用户自己注册过于难用，就转自建代理——AI 客户端已隔离在 `ai/`，换接法只改那一层。
