# 阶段 5 · 测试与验证

> **骨架 + 待填。**
> 这一阶段的判据全在你自己身上，没有别人能替你填。

## 目标

用真实使用证明它有用。

**不是自测。** 打开它、点两下、说"能用"，那不算。

## 这一阶段要回答的核心问题

**它真的被我用起来了吗？三类痛点有没有变好？**

## 待填：真实使用记录

**记什么**：每一次真实使用，用它做了什么，它帮上了没有，卡在哪。

**为什么必须记流水**：没有流水，后面三类痛点的判定就只能是印象；而印象对这件事特别不可靠。你会记住"它挺好用"或者"我大概没用几次"，两头都可能错。

**判定门槛**：是否已经发生过足够多次真实使用，能够支撑下面的每一条判定。次数由你自己定，但要写在完成标准那里。

> **本阶段的真实使用次数门槛：___ 次**

## 待填：三类痛点逐条判定

**每条都要判，一条都不许跳过。** 跳过的那条通常是没改善的那条。

**判定只有三个值**：改善 / 没改善 / 待观察。**不许写"部分改善"**。那是没改善的委婉说法，会让你算不清账。

| 痛点 | 判定 | 依据（哪一次使用 / 哪条记录） |
| --- | --- | --- |
| 启动不了（起不来 / 不想动 / 动了会愧疚，可分列） | | |
| 决策内耗 | | |
| 留不住东西 | | |

**依据要能指到具体某一次使用**（例如"第 7 条记录那次"），不能写"感觉比以前好一点"。

## 若未通过，回到

**核心闭环没被真实使用过，或次数远低于门槛** → 回 [阶段 4](07-开发.md)，先查清"我为什么不用它"。**不要先加功能**。加功能解决不了"不想打开"。

**三类痛点里最痛的那条判定是"没改善"** → 带上使用记录回 [阶段 2](05-定义-PRD.md) 重新定义问题。这是正常路径，不是失败。

**判定填不出来，因为每条都能指到记录、但你说不清好不好** → 说明成功指标定得太虚。回阶段 2，把它改成能量出来的行为。

**"待观察"占了多数** → 使用次数还不够。继续记流水，别急着下结论。
