# 产品生命周期总览

## 这份文档干什么用

它是这个项目的推进地图：10 段路，每段要干什么、产出什么、以及**怎样才算这段走完了**。

唯一的过关判定在 [阶段门清单](阶段门清单.md)。本文件只讲地图和顺序，不重复标准内容。标准只写在一处，才不会漂移。

## 整张地图

```mermaid
flowchart LR
  P01["01 立项与边界"] --> P02["02 用户调研"]
  P02 --> P03["03 市场分析"]
  P03 --> P04["04 竞品分析"]
  P04 --> P05["05 定义-PRD"]
  P05 --> P06["06 设计"]
  P06 --> P07["07 开发（含 AI 能力）"]
  P07 --> P08["08 测试与验证"]
  P08 --> P09["09 发布"]
  P09 --> P10["10 运营与迭代"]
  P10 -. 发现新问题 .-> P05
  P07 -. 技术不可行 .-> P06
```

## 为什么是这个顺序

每一段都是下一段的前提，倒过来做就会返工：

- **01 定不下"不做什么"，02 就会变成没完没了的观察。**
- **02 没有真实场景，05 里的功能就是凭空想出来的**，后面做得再漂亮也是在解决想象出来的问题。
- **03 没弄清市场位置，04 的竞品就不知道该跟谁比。**
- **04 没看清别人做成了什么，05 的差异化就没有依据。**
- **05 的 MVP 范围没收窄，06 就没有设计边界**，会一路设计到明年。
- **06 没定"几步之内必须把它叫出来"，07 会一路加功能**，桌宠变成又一个没人打开的应用。
- **07 没做出闭环，08 没有东西可验证**，只剩下自己点两下说"能用"。
- **08 没有真实使用记录，09 发布出去心里没底**。
- **09 装不上、说不清数据去哪了，10 无从谈迭代。**

## 三条关于顺序的补充理由

这三条来自对原来那套九步流程的复盘，值得单独记下来。

**一、先做便宜的验证，再做贵的分析。**

02 的用户调研成本低，能推翻"这个问题真不真"；03 的市场分析成本高，只能推翻"这个赛道值不值得进"。顺序反了，可能花一天做完市场分析，最后发现痛点是自己想出来的。

**二、01 不能省。**

立项要写死三件事：为谁解决什么、不做什么、预判怎么失败。不做的话，05 砍范围时没有剪刀，任何需求看起来都值得做，最后一定加满。

**三、05 与 08 在个人产品里换了含义。**

设计（06）必须排在技术选型之前，反过来会让界面被技术框死。测试（08）不是找 bug，是自己真实用一段时间，判据是"我下次还会不会主动打开它"。

## 10 段各自的一句话

| 阶段 | 一句话目标 | 核心产出 |
| --- | --- | --- |
| 01 立项与边界 | 把冲动变成有边界的假设 | 一页立项书：为谁解决什么、不做什么 |
| 02 用户调研 | 把自己真实的失控瞬间捞出来 | 场景卡、假设清单、痛点优先级 |
| 03 市场分析 | 判断这个位置值不值得占 | 市场规模、竞争格局、双结论 |
| 04 竞品分析 | 看清别人在什么位置上做成了什么 | 竞品名单、四层分析、行动点 |
| 05 定义-PRD | 把范围砍到能做完且真能用 | PRD：功能清单、页面原型、成功指标 |
| 06 设计 | 定下用什么实现它 | 技术约束、数据模型、技术选型 |
| 07 开发 | 做出能天天用的最小闭环，含 AI 能力 | 可运行版本、AI 能力验收表 |
| 08 测试与验证 | 用真实使用证明它有用 | 使用记录、三类痛点逐条判定 |
| 09 发布 | 让自己和未来的别人装得上 | 可分发构建、使用说明、隐私说明 |
| 10 运营与迭代 | 判断继续、转向还是停 | 迭代日志、去留决策 |

## 每段固定四件事

打开 `docs/` 里任何一份阶段文档，结构都一样：

**目标**：这一段为什么要存在
**这一阶段要回答的核心问题**：一段只问一到两个问题，答不上就不算走完
**产出物**：纸张层面要留下什么
**完成标准**：见下

## 完成标准：四条式

一个阶段要算做完，下面四条必须全部成立：

| 条目 | 含义 | 反例 |
| --- | --- | --- |
| **A 产出物存在且完整** | 东西真的在那里 | "我脑子里已经想过了" |
| **B 有证据** | 能指给别人看的记录、截图、原型、数据 | "我觉得差不多能用了" |
| **C 下游输入齐备** | 下一阶段能直接开工，不用回来补 | "做的时候再回头看需求" |
| **D 核心问题已用一句可证伪的话写死** | 这句话将来被事实推翻时，你就知道该回到哪一段 | "总之体验要流畅" |

只写"产出 PRD"是没法判断做完没做完的。加了 B，主观感受被挤出去；加了 C，返工被挤出去；加了 D，你才有一个回去修的入口。

## 判定规则

1. 只有 [阶段门清单](阶段门清单.md) 里的勾选项算数，别的地方写的标准不作数。
2. **全部勾选** → 进入下一阶段。
3. **有任何一条没勾** → 回到该阶段文档末尾写明的「若未通过，回到」。
4. 不允许"差不多就行"。这一条是整个体系里唯一不能通融的地方。

## 回退不是失败

地图上那两条虚线（7 → 2、4 → 3）是正常路径，不是出错。

带着新的证据回到更早的阶段，比硬着头皮把后面所有阶段重做一遍便宜得多。产品做不下去的原因很少是"不够努力"，多数是"带着错的假设往前冲"。
