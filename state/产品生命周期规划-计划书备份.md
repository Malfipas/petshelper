## Product Overview

一个面向个人长期使用的 AI 桌宠日常助手，以桌面陪伴形象存在，在不影响办公视觉的前提下便捷唤出，用来解决五类日常困境：做事启动难、日常规划模糊、做事半途而废或拖延、对已完成事件忘性大、每天重复的必做项目不想做。

本轮交付的不是桌宠本体，而是"像真产品经理一样把这件事做下去"的规划体系：把产品从想法到长期使用的全过程拆成有序阶段，并为每个阶段定出能勾选、能举证的完成标准。

## Core Features

- 全周期阶段地图：立项与边界、发现、定义、设计、开发、测试与验证、发布、运营与迭代，共 8 段，明确呈现阶段之间的顺序与依赖，而非并列清单
- 每阶段固定四件事：目标、这一阶段要回答的核心问题、产出物、完成标准；缺一不算过
- 完成标准采用统一四条式：产出物存在且完整、产出物有证据、下游阶段输入已齐备、核心问题已用一句可证伪的话写死
- 一份集中的阶段门清单作为唯一判定入口，全部勾选才进入下一阶段，未通过回到该阶段指定的回退点
- 五类痛点逐条覆盖到底：每类需有真实发生过的具体场景，并在测试阶段逐条给出"改善／没改善／待观察"的判断与依据
- 桌宠形态的两条理由（不遮挡办公视觉、增加陪伴感）落为可验证的设计约束，唤出路径以可数步数定义上限
- AI 能力并入开发阶段，但独立验收：固定用例集、通过率下限、失败样例留档
- 恢复入口：任何时刻都能立刻回答"我在哪、下一步是什么、当时为什么这样做"
- 每次回答开头标注本次是否调用了 adhd-friendly-output

## 交付形态与文档架构

### 技术选型

- 交付物为纯文档，本轮不产出可运行代码，不搭工程脚手架
- 文档格式：Markdown（UTF-8），纯文本便于逐阶段 diff、评审与迁移
- 版本管理：git，阶段门通过时打标签，让"过没过"这件事在提交历史里可追溯
- 单一来源：全部阶段门集中在 `docs/阶段门清单.md`，各阶段文档只引用不复制，避免标准漂移
- 状态随项目存放：恢复入口文件写在项目内的 `state/` 目录（`d:/桌面/正式作业/大四上/AI桌宠日常助手/state/`），该目录即本项目的状态根目录，覆盖 skill 默认的全局 STATE_ROOT。不写进 skill 目录（skill 目录会被安装脚本镜像覆盖）
- `state/` 随项目一起存放，是否纳入版本控制由你决定

### Implementation Approach

核心策略是把"产品生命周期"落成两样东西——**阶段地图**（顺序与依赖）与**阶段门**（可勾选的出口准则），再做逐阶段的骨架文档。

每份阶段文档使用同一骨架：目标 / 要先回答的问题 / 产出物 / 完成标准（A-D 四条）/ 回退点。判定规则统一为：全部勾选才推进，未过就回到写明的回退点，不允许"差不多就行"。

关键决策与理由：

- **完成标准四条式**：单靠"产出物存在"会写出无法判定的标准，加上"有证据"和"下游输入齐备"才能把主观感受挤出去
- **阶段门集中成一份清单**：标准散落在八个文档里必然漂移，集中后只有一处需要改
- **AI 能力独立验收**：AI 输出不确定，功能"能跑"不等于"可用"，所以用固定用例集 + 通过率下限 + 失败样例留档来判定
- **不预填阶段 1-7 的实质内容**：这些内容必须来自用户真实经历，凭空生成就是编造。先给骨架和判定标准，再逐阶段与用户一起填，这是本计划最重要的准确性约束
- **痛点闭环优先**：五类痛点必须一路走到测试阶段的逐条判定，而不是在定义阶段列完就不管
- **状态文件放在项目内**：恢复入口与项目同生共死，换机器或归档时一起带走，不需要额外记住一个外部路径
- 复杂度与开销：本任务以文本组织为主，无运行时性能问题；主要成本是文档之间的引用一致性，用集中式阶段门清单 + 固定编号解决

### Implementation Notes

- 全程遵守 adhd-friendly-output：人话先行、术语首次出现即就地解释、不给时长与截止（凡需要"持续使用"的判定一律改写为"发生过 N 次真实使用"）、不评价用户状态、每份文档控制在一个人能一口气读完的密度、每次回答开头标注是否调用该 skill、会话收尾加一句「这轮有没有帮到你？」
- 保留用户原始措辞：五类痛点表述与桌宠存在的两条理由原样入档，不做同义改写
- 文档编号固定为 00-08 与 `阶段门清单.md`，新增只往后追加编号，不改动已有编号
- 每交付一项即追加恢复入口文件（位置 / 下一步 / 为什么这样 / 已定），只追加不重写历史；「已定」是恢复时的主入口
- 恢复入口文件写在项目内 `state/` 目录下，命名用用户的说法：`state/AI桌宠日常助手-产品规划.md`
- 本项目 `state/` 目录只新增本任务专属文件；不改动 `d:/桌面/正式作业/大四上/ADHD学习研究/state/` 下已有的 `state-words.md`、`profile.md`、`observations.md`
- 控制波及面：本轮不动工作区内任何其他目录，不写代码文件，不做技术选型的实现验证

### Architecture Design

文档分三层：总览层给出阶段地图与依赖；判定层（阶段门清单）是唯一出口准则；执行层是八个阶段文档与可复用模板。

```mermaid
flowchart LR
  P0[阶段0 立项与边界] --> P1[阶段1 发现]
  P1 --> P2[阶段2 定义]
  P2 --> P3[阶段3 设计]
  P3 --> P4[阶段4 开发 含AI能力]
  P4 --> P5[阶段5 测试与验证]
  P5 --> P6[阶段6 发布]
  P6 --> P7[阶段7 运营与迭代]
  P7 -. 发现新问题 .-> P2
  P4 -. 技术不可行 .-> P3
```

## Agent Extensions

### Skill

- **adhd-friendly-output**
- Purpose: 作为全程输出规范，约束所有规划文档与对话回复的形态——人话先行、术语就地解释、不给时长与截止、不评价用户状态、每份文档保持单次可读完的密度、每次回答开头标注是否调用本 skill
- Expected outcome: 阶段文档与阶段门清单均为可直接照着做的形态，用户中断后无需回翻聊天记录即可接上

- **research**
- Purpose: 在阶段 1（发现）中完成"现有替代方案扫描"——查清番茄钟类、习惯打卡类、待办类工具对五类痛点各自覆盖到哪里、又在哪里失效
- Expected outcome: 一份有来源的替代方案失效点清单，直接进入 02-发现.md，作为"为什么现有工具解决不了"的证据，并与用户自述失效原因对齐

- **prototype**
- Purpose: 在阶段 3（设计）用一次性原型回答两个设计疑问——桌宠如何在办公时不被遮挡又能一键唤出、唤出路径能否压到约定的步数上限内
- Expected outcome: 一个用完即弃的原型与结论记录，写入 04-设计.md；结论无论成败都入档，失败结论用于修正设计约束
